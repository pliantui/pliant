## manifest

Use the `manifest` command to generate a manifest for each component in your ui folder. A manifest says what users may change about a component: which values of its props they can pick, whether they can rename or hide it, and which default states they can set.

```bash
npx pliantui manifest
```

The command reads your components' `cva` and `tailwind-variants` (`tv()`) definitions as source code. It never runs your code. It shows what it found, lets you accept or change it, and then writes the manifests.

```txt
Usage: pliantui manifest [options]

generate manifests for the components you already have

Options:
  -y, --yes                    skip the review and use the inferred classes.
                               (default: false)
  -c, --cwd <cwd>              the working directory. defaults to the current
                               directory. (default: "/home/you/my-app")
  -n, --namespace <namespace>  the namespace for component kinds. defaults to
                               the saved one, or app.
  -h, --help                   display help for command
```

### Where it looks

The ui folder comes from the `ui` alias in `components.json`, resolved through the `paths` in your `tsconfig.json` or `jsconfig.json`. Every `.ts`, `.tsx`, `.js` and `.jsx` file in it is read, including subfolders. Tests, stories and type declarations are skipped. In a TypeScript project, `.js` and `.jsx` files are read only when `allowJs` is set in `tsconfig.json`.

### What it reads

The command finds calls to `cva` from `class-variance-authority` or `cva`, and to `tv` from `tailwind-variants`. That includes renamed imports like `import { cva as variants }`, namespace imports like `CVA.cva(...)`, re-exports from your own modules like `export { cva } from "class-variance-authority"` or `export * from "class-variance-authority"`, and a `tv` you made with `createTV()`. `export *` re-exports are followed through the installed package, so the library must be installed for those.

The config can be written inline or kept in a `const`. It can also be imported from another file, spread from other objects, or wrapped in `as const` or `satisfies`. A call declared inside a component works too. `defaultVariants` and `compoundVariants` are read as well, and definitions that use `slots` and `extend` work too. A `null` default in `defaultVariants` means the variant has no default.

A prop goes into a component's manifest only when the value the user passes reaches the definition unchanged:

- directly: `buttonVariants({ variant, size })`, or through an object kept in a `const`: `const options = { size }`, then `sizeVariants(options)`
- through a fallback: `variant ?? "default"`
- through a props spread: `badgeVariants({ ...props })`. Keys written after the spread are fixed by the component and aren't exposed, and neither are props destructured out of it, like `tone` in `({ tone, ...props })`.
- through another component that has a manifest: `<Button size={size} />` or `<PaginationLink {...props} />`
- through a context provider, like a toggle group passing `variant` to its items. The summary notes that a value set on the group wins over the item's own.

Values the component works out itself, like `variant: isActive ? "outline" : "ghost"`, are not exposed, not even when the prop is typed as a string union. Neither is a prop the component assigns to, like `size = "sm"` or `({ size } = other)` inside the function. An options object the command can see being changed after it's created, by a property assignment, `delete` or `Object.assign`, isn't followed either. Static reading can't catch every change, so the review is where you correct anything it inferred wrongly.

A literal default on a destructured prop, like `size = "icon"`, wins over `defaultVariants`.

Props typed as string unions in the component's own types, like a sheet's `side?: "top" | "right" | "bottom" | "left"`, are listed too, as needing confirmation.

### How values are classified

Every value gets one class:

| Class              | Meaning                                  | Assigned to                                                                                                                                                                                  |
| ------------------ | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| user               | Users can pick it                        | Plain visual values, like `outline`, `ghost` or `lg`                                                                                                                                         |
| semantic           | Shown, but users can't pick it           | Values whose name contains destructive, danger, error, warning, caution, success or info; every value of a `severity` prop, and every value of a `status` prop whose values aren't UPPERCASE |
| state              | Not shown, because the component sets it | Props like `loading`, `disabled` or `isActive`; a `status` prop with UPPERCASE values                                                                                                        |
| needs confirmation | Left out until you confirm it            | Colour names like `red`, `none`, `link`, number keys, `true`/`false` variants and string-union props                                                                                         |
| hidden             | Left out because you chose so            | Set in the review                                                                                                                                                                            |

### Default states

A `default*` prop that pairs with a controlled prop in the component's props type, like `defaultOpen` with `open` or `defaultValue` with `value`, can become a default state that users set for themselves. This includes props from Radix and other libraries; React's own form attributes don't count.

Each one needs confirmation. A boolean, a date or a union of literals can be used as it is. A number needs a range, and a string needs the list of values users may choose from. You give these in the review.

### The review

After the summary, the command asks:

1. **Accept these classes?** Answer no to choose, per component, which values users can set and which they see but can't set, and which components users can rename or hide.
2. **These need your confirmation. Which can users set?** Anything you don't select stays out.
3. For each default state you kept, the values or range it needs, and whether users' own changes to it are saved automatically.

Your answers are saved, so later runs only ask about values they haven't seen before. Pass `--yes` to skip the review. Everything that needs confirmation is then left out, and the command says how many items were left out. If you cancel the review, nothing is written.

The review needs an interactive terminal. In CI or other scripts, pass `--yes`.

### Output

The command writes two files to the `pliant` folder inside your `lib` alias:

- `manifests.generated.ts`, or `.js` if `components.json` sets `tsx: false`. It exports `manifests`, keyed by the exported component name. Don't edit it by hand; run the command again instead.
- `manifest-decisions.json`, your review answers and namespace. Commit it. A `--yes` run with the default namespace and no saved answers doesn't create it.

Every component that calls a `cva` or `tv` definition gets a manifest. By default users can rename and hide it, even when none of its values were confirmed. A component with no definition, like a sheet whose `side` is a typed union, gets a manifest once you confirm one of its props or default states.

Each manifest's `kind` is `namespace:component-name`, like `app:button`. Bare kinds are reserved for Pliant's built-in components. The namespace defaults to `app`. Pass `--namespace acme` to use your own. It must be kebab-case, at most 32 characters, and can't be `pliant`. The namespace is saved, so later runs keep the same kinds.

The decisions file looks like this:

```json title="lib/pliant/manifest-decisions.json"
{
  "namespace": "app",
  "components": {
    "Button": {
      "props": {
        "variant": {
          "default": "user",
          "destructive": "semantic",
          "link": "hidden"
        }
      },
      "capabilities": { "hideable": false }
    },
    "Tabs": {
      "defaults": {
        "defaultValue": {
          "class": "user",
          "values": ["overview", "activity"],
          "persist": true
        }
      }
    }
  }
}
```

You can edit it by hand and run `npx pliantui manifest --yes` to apply it.

### What's reported, not guessed

When the command can't read something as written, it says so and leaves it out instead of guessing:

- a variant with a computed key, like `[accent]: "..."`
- values built at runtime, like `Object.fromEntries(...)`
- a config returned by a function: the component is marked **variants not readable**, and its variants from that definition are left out
- an argument the command can't follow, like `sizeVariants(makeOptions(size))`: the props that reach it are marked **values not readable**
- a `cva` or `tv` call that can't be traced back to its library
- `defaultVariants`, `compoundVariants` or `slots` nested inside `variants` by mistake
- a compound variant that refers to a variant or value that doesn't exist
- a prop that gets different defaults from two definitions: no default is set
- a default state whose type can't be stored, like `string[]`

Each report gives the file and line.

## scan

Use the `scan` command to list the node ids on each surface of your app: its regions, their slots, its tables and their columns, and which node holds which. Core uses this inventory to tell a node that doesn't exist from one that just isn't on screen yet.

```bash
npx pliantui scan
```

Like `manifest`, it reads your source code and never runs it.

```txt
Usage: pliantui scan [options]

list the node ids on each surface of your app

Options:
  --check          fail when the saved inventory is out of date, without writing
                   it. (default: false)
  --json           print the result as JSON. (default: false)
  -c, --cwd <cwd>  the working directory. defaults to the current directory.
                   (default: "/home/you/my-app")
  -h, --help       display help for command
```

### What it reads

The command reads the files your `tsconfig.json` or `jsconfig.json` includes, skipping tests, stories, type declarations and folders whose names start with a dot, like `.next`. It finds each `PliantRoot` from `@pliantui/react`, reads its `surface`, and follows what it renders, through your own components, across files. Pliant's exports are found through named, renamed and namespace imports (`import * as Pliant from "@pliantui/react"`), and through your own re-exports.

- a call to `usePliantRegion` or `useRegionSlots` is a region. The keys of its slots object are its slots, in order, and each slot holds what it renders. `PliantRegion` calls `usePliantRegion` with its `id` and `slots` props, so `<PliantRegion id="key-metrics" slots={{ revenue: <KpiCard /> }} />` is the region `key-metrics` holding the slot `revenue`. A region rendered as the slot of the same id is that slot.
- a call to `usePliantTable` from `@pliantui/react/table` is a table. Its columns are read as TanStack names them: `id`, else `accessorKey` with dots as underscores, else a string `header`. Arrays of column defs and `columnHelper.columns`, `accessor`, `display` and `group` are read, also inside a `useMemo`. A column is listed by its address, like `orders-table/columns/customer`.
- a call to one of your own hooks, like a `useOrdersTable` that returns `usePliantTable(…)`, is followed into that hook, also when it's called as `hooks.useOrdersTable()`. The hook's arguments aren't followed, so write the ids and slots inside the hook; an id or slots object that comes from an argument is reported.
- a component that declares one region or table puts everything else it renders in it, and a slot holds everything rendered in it. A component that declares several, directly or through your own hooks, puts everything else where the component itself sits, since a region or table renders no element of its own.
- a render prop, like `renderItem={(item) => …}`, is followed to where the component calls it.
- what a component renders is what its returned JSX reaches: nested JSX children, the props of component elements, `.map`, `.flatMap` and `.filter` callbacks, conditionals and logical operators, local variables that hold JSX, render props, and your own functions called to render, like `{renderRows()}`. JSX made anywhere else, like in an effect, an event handler or a function passed to another call, isn't rendered there, and neither are the props of HTML elements or event handler props like `onPick` on a component.
- a region or table a component declares is placed where the component first renders it, as above: where its value, a member of it, or an item of it is a JSX child (`{region.entries.map(…)}`, `{region.entries[0]}`, `{region}`), or is passed to a component as a prop or in a spread (`<DataTable table={table} />`, `<DataTable {...table} />`). Reading a list's `length`, like `{region.entries.length}`, doesn't count. That place gives the slots of a lone region their order among the component's other nodes, and gives each of several regions and tables its parent and order. The value can be the variable that holds the hook's result, a value destructured from the call or from that variable (`const { entries } = …`), or, for one of your hooks that returns several as an object, that one's own member (`both.a`). When the command finds no such place for a region, or for one of several tables, as with regions a hook returns in an array, the nodes are still listed, last, with a warning, and the surface is marked as not read in full. A lone table holds the rest of its component's output, so it's listed where the component is.

A `PliantRoot` in an App Router layout (`app/**/layout.tsx`) that renders `{children}` holds the pages under that layout: the page of its own segment, and the pages of nested segments, each inside the nested layouts between. Route groups like `(shop)` and dynamic segments like `[id]` are followed like any other segment. A parallel route folder, like `@modal`, holds what the layout renders as the prop of the same name, `{modal}`, through the folder's own `layout` if it has one. An `@children` folder adds to the layout's `children`. A page's default export can be wrapped in a call, like `export default withAuth(function Page() { … })`. Private folders (`_components`) and intercepting routes aren't followed, since they don't render as the layout's props. Only `layout` files in the project's App Router folder count: `app`, or `src/app` when there's no `app`, as Next.js picks it.

Ids can be written inline, kept in a `const` or imported, or passed down as props, as `PliantRegion` passes its own. Content rendered conditionally, like `{open && <PliantRegion … />}` or either side of a ternary, is listed too: the inventory is every node that can exist, not the ones on screen now.

### Output

The command writes `inventory.generated.ts` to the `pliant` folder inside your `lib` alias, next to the manifests, or `.js` if `components.json` sets `tsx: false`. It's a module rather than JSON, so your app imports it like any other file. Don't edit it by hand; run the command again instead, and commit it.

It exports `inventory`, keyed by surface. Each surface has:

- `baseIds`: the surface's ids, sorted, as `{ ids, source }`.
- `baseParents`: each node id mapped to the id of the node that holds it, or `null` at the top of the surface. Columns aren't nodes, so they aren't in it; their address names their table. Its key order carries no meaning.
- `baseOrder`: each node that holds other nodes, mapped to those nodes in the order they render, such as a region's slots in key order. Columns aren't listed; a table's columns keep TanStack's order.
- `ids`: what each id is, as `{ kind, hash }`. The kind is `pliant:region`, `pliant:table` or `pliant:column`, or for a slot, the kind of the component it renders. A slot that renders a component with a manifest from `pliantui manifest` takes that manifest's kind, like `app:badge`; any other slot is `pliant:slot`. The hash covers the kind and the manifest, so it changes when either does.

The kinds and hashes come from the manifests, so run `scan` again after `pliantui manifest`.

```ts title="lib/pliant/inventory.generated.ts"
export const inventory = {
  "/examples/orders": {
    baseIds: {
      ids: [
        "average-order-value",
        "key-metrics",
        "orders",
        "orders-table",
        "orders-table/columns/createdAt",
        "orders-table/columns/customer",
        "orders-table/columns/id",
        "orders-table/columns/notes",
        "orders-table/columns/region",
        "orders-table/columns/status",
        "orders-table/columns/value",
        "overdue",
        "revenue",
      ],
      source: "inventory",
    },
    baseParents: {
      "average-order-value": "key-metrics",
      "key-metrics": null,
      orders: "key-metrics",
      "orders-table": null,
      overdue: "key-metrics",
      revenue: "key-metrics",
    },
    baseOrder: {
      "key-metrics": ["revenue", "orders", "average-order-value", "overdue"],
    },
    ids: {
      "average-order-value": {
        kind: "pliant:slot",
        hash: "a220a621c23f938c",
      },
      // … one entry per id
    },
  },
} as const
```

`baseIds`, `baseParents` and `baseOrder` have the shape core's `resolveLayers` and `validateOverlay` take, so you can pass a surface's entry as it is:

```ts
import { resolveLayers } from "@pliantui/core"

import { inventory } from "@/lib/pliant/inventory.generated"

const { baseIds, baseParents, baseOrder } = inventory["/examples/orders"]
const resolved = resolveLayers(overlays, {
  surface: "/examples/orders",
  baseIds,
  baseParents,
  baseOrder,
})
```

With the inventory, an op into a node that isn't listed is reported as `missing-container`, since that node doesn't exist anywhere on the surface. `baseParents` tells core which node holds which, so a node flagged `critical` also stays visible when an op would hide a node that holds it. `baseOrder` gives each group's order before any op, so a `destructive` action starts out where it renders relative to the `primary` one.

### What's reported, not guessed

When the command can't read something as written, it says so, with the file and line, instead of guessing:

- a computed id, like `id={regionId()}` or an id that comes from `.map`
- a computed slot key, like ``[`${prefix}-total`]: …``
- a spread in a slots object that isn't a plain object in a `const`, like `...extra`
- columns built at runtime, like `fields.map(...)`
- a `PliantRoot` whose `surface` can't be read
- a region or table that no `PliantRoot` renders, as far as the command can follow. Every surface that renders its file is marked as not read in full, or every surface when none does, since it may be rendered through code the command can't follow.
- a route whose default export can't be read as a component
- content passed as `children` or as a render prop that the command can't see, like a `PliantRoot` in a provider component outside a layout, whose `children` come from wherever it's used

When part of a surface can't be read, the inventory can't claim to be complete, so the surface's `baseIds` use `source: "mounted"` instead of `"inventory"`. Core's `baseIds` know only those two sources. With `"mounted"`, an op into a node that isn't listed is `dormant`: it waits until that node shows up, rather than being dropped as `missing-container`, since the node may be one the command couldn't read. The summary marks the surface as **not read in full**. Fix what the warnings point to and run the command again to get `"inventory"` back.

A column whose id isn't one overlays can address, like `2fa`, is left out with a warning: column ids must start with a letter and contain only letters, digits, `-` and `_`.

### Errors

These stop the command, and nothing is written:

- a slot id that starts with a digit, like `"2024"`. JavaScript moves integer-like keys before every other key of an object, so the slots would render out of order.
- a region or table id that isn't kebab-case or doesn't start with a letter.
- a node id used twice on a surface, in two different places or as two different things.

### In CI

Run `scan` with `--check` in CI. It exits with code 1 when the committed inventory is missing or out of date, or when the scan finds an error, and writes nothing:

```bash
npx pliantui scan --check
```

Pass `--json` to get the inventory, errors and warnings as JSON, for scripts and agents. Without `--check`, it still writes the file, as a plain run does.
