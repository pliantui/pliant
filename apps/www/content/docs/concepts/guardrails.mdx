---
title: Guardrails
description: What users can never change, the parts of a page you can protect, and what Pliant doesn't protect.
---

Users can change how your pages look, but not what they do. Every change follows the rules below, whether a user made it by hand, with the ask panel, or it came from a team default. Some parts of a page can be protected further.

## Only changes from the catalog

A change is a list of [operations](/docs/concepts/operations) from a fixed catalog. It can't contain code, markup, CSS or a query. Labels are plain text and filter values are data, never interpolated into anything. A change can't name a single row of data, so it can only change how data is shown.

Each operation has fixed limits: at most 500 per change, layouts of at most four columns, column widths within the limits you set on the column, and so on.

## Users can hide what you built, but not delete it

Users can hide anything you built, and show it again. They can only remove what their own layer added, such as a section they grouped cards into. Clearing every change always brings back your page as you wrote it.

## Screen readers follow the visible order

When a user reorders a region, Pliant moves the elements themselves, not just their position on screen. Keyboard focus and screen readers follow the order users see. Tables keep the same promise for their columns.

## Some things are never saved

A table's page number lives only in the browser tab, so it's never saved or shared. Table filters stay in the tab too, unless you save them with `persistFilters`.

## The ask panel can only propose

The AI behind the ask panel can only answer with operations, and only the ones the part the user pointed at allows. It's told the names of your columns and cards, never your rows. Asks to act on data, such as "delete these orders" or "refund this", are turned away.

Every answer is checked on your server, then again in the browser. It shows as a preview, and nothing is saved until the user locks it in.

## Protecting parts of a page

Some parts of a page need protecting from well-meant changes. You mark them with **flags**, by address, in [pliant.config.ts](/docs/config#flags), and every page applies them:

```ts title="pliant.config.ts"
flags: {
  "/orders": {
    "orders-table/columns/status": { critical: true },
    "order-actions/slots/delete": { destructive: true },
    "order-actions/slots/save": { primary: true },
  },
},
```

A part flagged `critical` can never be hidden, and an action flagged `destructive`, such as **Delete**, can never move closer to the `primary` action, such as **Save**. With **Save**, **Cancel**, **Archive** and **Delete** in a row, a user can move Delete to the end or into the overflow menu, but not right next to Save. [pliant.config.ts](/docs/config#flags) lists every flag.

A change that would break a flag's rule is skipped, and the rest of the change still applies. When changes from several layers combine to break a rule, the one from the highest layer is skipped.

<Callout
  variant="warning"
  title="Not fully implemented yet"
  data-unfinished="not-implemented"
>
  Declaring flags in `pliant.config.ts` isn't in Pliant yet, and `PliantRoot`
  doesn't take flags. Today, flags apply when you pass them as `flags` to
  `resolveLayers` or `validateOverlay` from `@pliantui/core`.
</Callout>

## Rules for shortcuts, variants and forms

- Users can bind a keyboard shortcut to an action from its menu. A shortcut can't take keys the browser, the operating system or a screen reader relies on, such as <Kbd>Ctrl</Kbd> <Kbd>T</Kbd>, or keys another action already has. List your app's own shortcuts as `reservedShortcuts` in `pliant.config.ts`, and users can't take those either.
- A component's **manifest** is a short JSON description of what users may change about it. A manifest can mark some prop values as `semantic`, meaning they carry meaning, such as a button's `destructive` variant. Changes can't set a semantic value; only your code assigns it.
- A default a user or team sets on a form field must pass the field's schema, such as your Zod schema. Otherwise it's skipped.
- Form fields can move within their form, but never into another container, so they keep their focus and value.

<Callout
  variant="warning"
  title="Not fully implemented yet"
  data-unfinished="not-implemented"
>
  Binding shortcuts from the page and `reservedShortcuts` in `pliant.config.ts`
  aren't in Pliant yet. Today, the shortcut and variant rules apply when you
  resolve changes with `@pliantui/core`, which takes `reservedShortcuts` as an
  option.
</Callout>

## Team defaults aren't locks

A team or organization default is a starting point. Each user can still adjust anything it sets for themselves.

Any lock in a browser is a policy, not a security boundary: the code that applies changes runs on the user's device, and they control it. Anything a user must not see belongs in your server's permissions, so it never reaches the browser.

## Hiding a column doesn't protect it

Hiding a column or a card is a display preference. Hidden cards stay on the page, and hidden columns stay in the table's data.

<Callout variant="warning" title="Never use hide to protect data">
  If a user mustn't see a field or a row, leave it out of what your server sends
  them.
</Callout>
