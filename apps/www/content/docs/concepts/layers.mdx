---
title: Overlays and layers
description: How a user's changes are stored as overlays, and how organization, team, personal and session layers stack to decide what each user sees.
---

Every set of changes is stored as an **overlay**, a small JSON document. Overlays sit in **layers**, from organization-wide defaults down to a single browser tab, and stack on top of your page. Once you know the order they stack in, you can predict what each user sees.

## Overlays

An overlay holds a list of [operations](/docs/concepts/operations) for one surface and one layer. This one sorts the orders table by value and hides its notes column, for one user:

```json title="overlay.json"
{
  "v": 1,
  "id": "01JD5Z8Q9W3X4Y5Z6A7B8C9D0E",
  "surface": "/orders",
  "layer": "personal",
  "ops": [
    {
      "op": "setSort",
      "target": "orders-table",
      "sort": [{ "field": "value", "dir": "desc" }]
    },
    { "op": "hide", "target": "orders-table/columns/notes" }
  ],
  "basis": { "contract": 1, "core": "0.0.0", "manifests": {} },
  "source": "manual",
  "createdBy": "user_123",
  "createdAt": "2026-11-20T09:30:00Z"
}
```

You rarely write overlays by hand. Pliant creates them as users work, and your storage keeps them. An overlay saved by a newer version of Pliant loads in an older one without losing anything, and changes the older version doesn't know are skipped, not lost.

Every field of an overlay is listed in the [overlay format reference](/docs/reference/overlay).

## Layers

Your page as you wrote it is the base. Four layers stack on top of it, from lowest to highest:

| Layer      | Who it's for                | How long it lasts                                 |
| ---------- | --------------------------- | ------------------------------------------------- |
| `org`      | Everyone in an organization | Until it's changed                                |
| `team`     | Everyone on a team          | Until it's changed                                |
| `personal` | One user                    | Every visit, on every device your storage reaches |
| `session`  | One user, in one tab        | Until the tab closes                              |

The `session` layer holds things that shouldn't follow a user around: the table's current page, its filters unless you save them, and an ask panel preview the user hasn't kept yet.

Pliant loads `org` and `team` overlays from your storage along with the user's own. See [Storage](/docs/storage).

## Higher layers win, per property

When two layers change the same property, the higher layer wins. Different properties never conflict.

- A team sorts `orders-table` by value, and a user hides its notes column. **Both apply.**
- The user then sorts by date. **The user's sort wins**, because both change the table's sort. Sorts replace each other whole; they don't merge field by field.
- A team filters on status and the user filters on region. **Both apply**, because filters are kept per field.

Moves are placed relative to other items, such as "before revenue", so hiding a card never breaks another layer's move.

## Several overlays in one layer

A layer can hold many overlays: a user may have changed the page many times, or belong to several teams. They apply in a fixed order, and the later one wins:

- Team overlays follow the `teamOrder` you pass to `PliantRoot`, highest precedence first. Teams you don't list rank below those you do.
- Then, in every layer, older overlays apply before newer ones.

The result never depends on the order your storage returns overlays in.

## Undoing your own scope

Users can hide anything, but they can only remove what their own layer added. A user can hide a section their team added, but can't delete it from the team's layer.
