Pliant lets users change how your pages look. It never decides what data they may see: your server does. This section explains where each protection lives, so you can tell which ones are security boundaries and which ones only guard against mistakes.

## Where each protection lives

| Protection                                         | Enforced by                                                      | A security boundary?               |
| -------------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------- |
| Which rows and fields a user may load              | Your datasets, on your server                                    | Yes                                |
| Who may ask the AI, and who may save team defaults | Your `getUser` and `canPublish`, on your server                  | Yes                                |
| What a change can contain                          | The operation catalog, checked on your server and in the browser | Yes, for stored and shared changes |
| What the AI is told                                | The ask route, on your server                                    | Yes                                |
| Parts users can't hide or move                     | Guardrails, in the browser                                       | No                                 |
| Hidden columns and cards                           | The browser                                                      | No                                 |

The rule of thumb: anything a user must not see belongs in your server's permissions, so it never reaches their browser. Everything that runs in the browser, including guardrails, protects users from mistakes, not from themselves.

## Changes are data, never code

A change is a list of [operations](/docs/reference/operations) from a fixed catalog. It can't hold code, markup, CSS or a query, and calculations are [expressions](/docs/concepts/expressions) that Pliant interprets itself: nothing is passed to `eval` or `new Function`. Labels are plain text and filter values are data, so a shared or AI-made change can't inject anything into your page.

A saved change that contains a malformed or unknown operation still loads: Pliant applies the valid operations and skips the rest. An AI answer is accepted only when every operation in it is valid.

## What your server checks

- The ask route, `createPliantHandler`, answers 401 unless your `getUser` returns a user. It accepts only JSON bodies up to 32 KB, which keeps cross-site form posts from spending a signed-in user's model budget. Each model call times out after 15 seconds by default, and an answer can make at most 8 tool calls.
- The storage route, `createStorageHandler`, answers 401 without a user, validates every overlay before storing it, and saves to a team or organization layer only when your `canPublish` allows it. It assigns every version and timestamp itself, and records the signed-in user as the author of each stored version.
- Datasets require a `scope` for every user, and a missing scope fails closed. `compileQuery` builds parameterized queries, so filter values never become SQL.

## What you need to add

- Authentication: both routes call your `getUser`. Return `null` for anyone who isn't signed in.
- Rate limits and quotas on the ask and storage routes. Neither route limits how often a user calls it.
- Permissions on every dataset. See [Permissions](/docs/security/permissions).
